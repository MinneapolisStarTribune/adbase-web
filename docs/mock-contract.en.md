## Previous-year candidates (2026-11-25)

Queries include zero-amount candidates for advertiser/product combinations persisted in the immediately preceding year but absent from the selected year in the same territory. Keys are trimmed and compared without case; current-year records, including all-zero records, take precedence. Candidates have a distinct row kind and stable UI key, without a persisted ID, version, or update attribution. Reading, filtering, paging, and cancelling never persist candidates. Unsaved candidates cannot seed another year or enter exports.

Deduplication occurs before advertiser filtering. Search uses each retained row's name snapshot: the current-year name when a current record exists, otherwise the previous-year name. This deliberately prevents an old name search from manufacturing a candidate for a combination already saved under a new name. The legacy update instead filters each year's SQL result before combining it. Pagination counts candidates and uses advertiser name followed by a stable row key; annual totals still use only persisted current-year records.

Saving a candidate uses the existing create endpoint with the target year and fixed dimensions. Later edits use the new record's ID and version. Current advertiser/product availability is checked again on the server; unavailable candidates remain visible with an explanation and disabled Save. Concurrent creation of the same combination returns 409; cancel and refresh the query to load the saved row. These availability and historical-name decisions remain explicit mock behavior pending production business confirmation.

To demonstrate with the initial metadata, select North / 2027: 35 zero candidates span two pages. North / 2028 stays empty until 2027 records are saved. Central / 2027 shows the prior `special` product but blocks saving because its availability is limited to 2026.

## Permission matrix

| Operation               | Representative       | Delegate                           | Administrator   | Unassigned |
| ----------------------- | -------------------- | ---------------------------------- | --------------- | ---------- |
| Query, totals, choices  | Assigned territories | Assigned and delegated territories | All territories | Denied     |
| Create/update forecasts | Assigned territories | Assigned and delegated territories | All territories | Denied     |
| Advertiser maintenance  | Denied               | Denied                             | Allowed         | Denied     |
| Domo download           | Denied               | Denied                             | Allowed         | Denied     |
| Activity view           | Denied               | Denied                             | Allowed         | Denied     |

All business APIs require a valid session. Missing/expired sessions return 401, denied access 403, invalid input 400, absent records 404, and duplicate/stale writes 409. Mutations also require the expected Origin and JSON content type. Sample identity selection is available only while mock mode passes environment validation; production rejects it.

The in-memory session store has a replaceable interface. Multi-instance sessions, durable audit history, transactional SQL behavior and database round-trip precision cannot be validated by this mock implementation. The team must confirm those during the excluded integration work.
